## Phase 1 - Corrected pitch (confirmed 2026-07-22)

Overseer is a repo-local, host-agnostic project hygiene skill for solo operators whose AI context and project files become stale, duplicated, ambiguous, or disorganized over time. When invoked by any capable agent host, Overseer inspects the repository, maintains one clean root `overseer.md` context-health note, and proposes evidence-backed documentation or file-lifecycle remediation. After explicit approval, it may repair human-maintained documentation and organize project artifacts by renaming, moving, archiving, or removing them. Overseer does not create domain work products or rewrite their contents. The host agent owns invocation, execution, and any scheduling, while domain-specific tools and skills create the actual work products.

### Confirmed boundaries

- Overseer is an independent, host-agnostic skill, not a standalone application, daemon, runner, or control plane.
- The primary problem is context-index entropy: obsolete entries, missing links, duplicates, ambiguous canonical references, weak descriptions, and stale project knowledge.
- The only required durable output owned by Overseer is one clean `overseer.md` note useful to humans and AI agents.
- Overseer may read project files and version-control state as evidence. It does not generate domain artifacts, but it may manage their lifecycle after approval.
- A file's canonical or superseded status must be explicit in the index. Filename recency alone is not reliable evidence.
- Index maintenance must avoid fabricating certainty when project evidence is ambiguous.
- Any capable host agent may invoke Overseer. Proxima is an optional host and integration target, not a dependency.

### Explicit non-goals

- Generate or rewrite the contents of invoices, reports, documents, images, CSV files, or other domain artifacts.
- Become a general source-code refactoring tool or artifact production workflow.
- Replace Proxima Archive, Tasks, Recipes, Satpam, or scheduling.
- Own a standalone UI, database, daemon, or execution runtime.

### Host compatibility and local-convention finding

Proxima's `wiki/index.md` is auto-generated by `rebuild_index()` as a catalog of Markdown notes under `wiki/`. Manual edits to that index can be overwritten. Overseer must therefore integrate as a complementary wiki note rather than create or compete with another `index.md`.

This is one host-specific convention, not Overseer's universal file contract. Overseer maintains exactly one `/overseer.md` at the repository root, next to root-level project instructions such as `AGENTS.md` or `CLAUDE.md`. Host integrations may point to this file but must not create a second Overseer note elsewhere.

### File contract - confirmed and host-agnostic

Overseer maintains exactly one `/overseer.md` note at the repository root containing current context-health state and a compact rolling history. It does not create a separate `index.md`, a wiki-specific duplicate, or one report file per routine audit.

The file separates current truth from history:

- current canonical references and their owners;
- active stale, duplicate, missing, or ambiguous-context findings;
- what the most recent Overseer run changed in the note;
- a compact history containing only material curation events, not a log line for every no-op scan.

### Patterns absorbed from FirstMate `/stow`

- **Discover before routing:** inspect existing project memory and documentation conventions before interpreting a path as authoritative.
- **Most-specific owner:** each fact points to its most specific authoritative source instead of being copied into `overseer.md`.
- **Inspect then update:** read the current destination, decide whether new evidence is new, duplicate, superseding, or obsolete, then edit intentionally.
- **Curate instead of append:** rewrite or prune an existing entry whenever possible. Do not let history become an append-only dump.
- **Supersession is explicit:** remove stale current-state prose while preserving only the small historical fact needed for recoverability.
- **Ambiguity stays visible:** ask once when two plausible sources conflict and retain the resulting routing decision so the same ambiguity does not recur.
- **No invented knowledge system:** use established local conventions and pointers. `overseer.md` is an integration note, not a replacement for `AGENTS.md`, project docs, wiki notes, or backlog systems.
- **Honest completion verdict:** each run states whether context is clean enough for an AI handoff and lists any unresolved findings that prevent that claim.

FirstMate-specific paths, backlog commands, fleet roles, and external routing are not absorbed. They solve a different operating environment.

### Documentation remediation policy - confirmed

- Every audit and scheduled run is read-only until a human approves a proposed remediation.
- Overseer may edit the authoritative project documentation after approval.
- It must show the evidence, affected source, intended replacement, and reason before requesting approval.
- After approved edits, Overseer re-scans the affected context, updates `/overseer.md`, and records one compact material-change history entry.
- An approval applies only to the presented remediation set. It is not standing permission for later scheduled runs.

### Tiered documentation write policy - confirmed

After approval, Overseer may update human-maintained, context-bearing documentation throughout the repository. Permission and remediation behavior depend on document class:

1. **Living context:** root and nested `AGENTS.md`, `CLAUDE.md`, `README*`, `CONTRIBUTING.md`, wiki notes, runbooks, and human-maintained project documentation may be corrected.
2. **Historical records:** ADRs, audit records, release notes, and other historical evidence are not rewritten to make the past look current. Overseer records a superseding pointer or flags the record when necessary.
3. **Protected or out of scope for content edits:** auto-generated files, `CHANGELOG.md`, vendored content, lockfiles, secrets, binaries, source code, and business artifacts are not rewritten by Overseer. Separately approved lifecycle operations may rename, move, or archive eligible business artifacts without altering their contents.

For `AGENTS.md`, `CLAUDE.md`, and equivalent high-authority instruction files, every proposed correction must identify the stale statement, contradictory repository evidence, file scope, exact intended diff, and expected effect on agent behavior. Style-only rewrites are not permitted.

### First-run bootstrap - confirmed

When `/overseer.md` does not exist:

1. inspect the repository without writing;
2. discover context-bearing documents, generated-file markers, nested instruction scopes, and candidate authoritative sources;
3. present a proposed baseline plus unresolved ownership conflicts;
4. obtain one explicit user confirmation;
5. create `/overseer.md` only after confirmation;
6. re-read the created file and report whether the project now has a trustworthy AI-context baseline.

The initial confirmation authorizes creation of the presented baseline only. It does not grant standing permission for future remediation.

### Product fate - confirmed

- Overseer is an open-source standalone skill repository licensed under MIT.
- It is installable independently into multiple capable agent hosts.
- Any compatible agent host may bundle, recommend, invoke, or schedule it under the same license, but no host is its source of truth or a required runtime.
- The core skill must work locally without a hosted service, account, or paid Overseer API.

### Language and public positioning - confirmed

- All masterplan documents, skill instructions, templates, examples, and user-facing copy are written in English.
- Public positioning names Codex, Claude Code, and other AI agents only when examples are useful.
- Host-specific prior art may remain in internal research notes, but it does not appear in the product pitch or create a runtime dependency.

### Recommended session-close workflow

Overseer should be used before ending a substantial AI-agent session, but the closing run is a lightweight **checkpoint**, not a full repository audit.

The checkpoint:

1. reviews the current conversation, decisions, repository diff, and files changed during the session;
2. identifies durable knowledge that exists only in the conversation or contradicts existing documentation;
3. classifies each finding as new, duplicate, superseding, obsolete, or unresolved;
4. proposes precise documentation changes with evidence;
5. applies only the approved remediation set;
6. refreshes `/overseer.md` current state and adds a history entry only when a material change occurred;
7. returns an honest safe-to-end verdict and a short resume pointer.

If the session produced no durable context change, the checkpoint is a no-op and must not add history noise.

A full repository audit remains a separate, less frequent operation for first-time baselines, major refactors, releases, migrations, or periodic maintenance.

### Relationship to `/stow` and artifact inspection

`/stow` and Overseer share inspect-then-update discipline but start from different evidence:

- `/stow` starts from the current conversation and captures durable knowledge that has not yet reached disk.
- Overseer starts from repository reality and reconciles the documentation and AI context against what now exists on disk and in version-control state.

Artifacts are evidence and lifecycle subjects within Overseer's scope. Overseer may inventory and selectively inspect documents, reports, invoices, images, datasets, generated HTML, and other outputs to determine whether context references are missing, stale, duplicated, ambiguous, or superseded. It does not create or rewrite those business artifacts, but after explicit path-specific approval it may rename, move, or archive them and repair affected documentation references.

Inspection depth is proportional:

- a session-close checkpoint examines artifacts created, modified, or referenced during that session;
- a full audit inventories all relevant project artifacts, then performs deeper content inspection only where metadata, relationships, or context disagree;
- ignored dependencies, build caches, vendored trees, secrets, and unrelated binary noise are excluded.

Example: if `invoice-v1.pdf` and `invoice-v2.pdf` both exist while documentation points to the first, Overseer flags the canonical-version ambiguity. After the user identifies the active invoice and approves a lifecycle plan, Overseer may rename the active file, move the superseded file into an established archive, repair documentation references, and update `/overseer.md`. Removal requires its own recoverability-aware approval.

### Artifact lifecycle scope expansion - confirmed

Overseer includes approval-gated file organization and cleanup for project artifacts and loose project files. Eligible actions are rename, move, group, deduplicate by selecting a canonical file, and archive. This capability exists to resolve project entropy rather than merely report it.

The capability does not authorize unrestricted deletion. Every proposed operation must name exact paths, explain why each file is affected, identify broken references or dependencies, state the recovery method, and receive approval for that bounded set. Broad globs, repository-root deletion, and silent scheduled cleanup are prohibited.

### Archive-only removal policy - confirmed

Overseer never permanently deletes project files. A cleanup operation may move an approved file into an archive while preserving its original path, reason, and canonical replacement where applicable. The owner is solely responsible for manually deleting archived files after deciding they will never be needed again.

- Tracked and untracked files follow the same archive-first product policy.
- Exact duplicates are still archived rather than deleted.
- Scheduled runs may propose cleanup but may not move files without approval.
- Moves must repair affected references and be recorded compactly in `/overseer.md`.
- A failed multi-file move must not leave documentation claiming the cleanup completed.

### Overseer-owned file layout - confirmed

- `/overseer.md` remains the single root-level context-health ledger so humans and AI agents can discover it beside files such as `AGENTS.md` and `CLAUDE.md`.
- All additional files owned by Overseer live under `/overseer/` and must not be scattered across project folders.
- The default archive root is `/overseer/archive/`.
- Archived files preserve their original relative directory structure beneath a dated archive boundary to prevent filename collisions and retain provenance, for example `/overseer/archive/2026-07-22/downloads/invoice-final.pdf`.
- If a project has an explicit archive convention that must be respected, Overseer uses a clearly namespaced Overseer area rather than placing managed files directly among unrelated archives. The proposed destination is shown for approval during bootstrap or remediation.
- Moving a file into the Overseer archive does not make Overseer the semantic owner of that artifact. It owns only the archive operation and its recorded provenance.

### Public modes - confirmed

- **`scan`** is the default lightweight mode. It inspects the current conversation, repository delta, and files or artifacts created, modified, or referenced during the current session.
- **`audit`** performs a repository-wide context and project-hygiene inspection using bounded exclusions and selective deep reads.
- **`clean`** processes reviewed findings. After approval, it may repair living documentation, rename or move eligible files, update affected references, and move superseded or unwanted files into the archive. It never permanently deletes files.

If `/overseer.md` is missing, any mode enters the confirmed first-run baseline flow before continuing. The shorter names are the complete public vocabulary; `checkpoint`, `reconcile`, `organize`, and `cleanup` are not separate modes.

### Mode write boundaries - confirmed

- `scan` and `audit` inspect first, present findings, and may update only root `/overseer.md` after explicit approval.
- `scan` and `audit` never modify other documentation or move project files.
- `clean` is the only mode that may change human-maintained documentation, organize eligible files, repair references, or move files into `/overseer/archive/`.
- `clean` requires a separate approval for the exact remediation set even when its findings were already approved for inclusion in `/overseer.md`.

### Clean approval granularity - confirmed

`clean` presents one remediation plan divided into three independently selectable groups:

1. **Documentation:** approved edits to living context documents and repaired references.
2. **Organize:** approved renames, moves, grouping, and canonical naming without removal from the active project area.
3. **Archive:** approved moves into `/overseer/archive/`, with no permanent deletion.

The owner may approve or reject each group independently. Approval of one group never implies approval of another, and unapproved findings remain unresolved in `/overseer.md`.

## Phase 3 - Product decisions complete

The product is an English-language, MIT-licensed, independent repository hygiene skill with three modes (`scan`, `audit`, `clean`), one root context ledger (`/overseer.md`), approval-gated documentation and file lifecycle changes, grouped clean approvals, and an archive-only removal policy. It has no UI, hosted service, account system, agent runtime, scheduling engine, or artifact-generation responsibility. It requires no incremental infrastructure budget beyond the user's existing agent host.

## Phase 2 - Absorption map

**Absorption level:** Assemble, with no code fork.

- Absorb FirstMate `/stow` heavily for inspect-then-update, most-specific ownership, replacement over accumulation, bounded history, and honest handoff verdicts.
- Discover and follow host-local context conventions. Proxima's wiki behavior is an optional adapter pattern, not a dependency or universal path.
- Absorb Aider's concise repository-map principle for bounded AI context.
- Absorb only the metadata, canonical identity, duplicate, and supersession concepts from Paperless-ngx and DVC. Do not adopt their storage or pipeline infrastructure.

**The one difference:** Overseer continuously reconciles a project's documented AI context against repository evidence, then proposes approval-gated corrections to the authoritative documentation. It does not capture a conversation like `/stow`, manage documents like Paperless-ngx, version datasets like DVC, or run agents like Proxima.

## Phase 4 - Stack ratification

**Chosen stack:** open Agent Skills folder plus Python 3 standard-library helpers.

- `SKILL.md` owns semantic workflow, evidence interpretation, approval interaction, and mode orchestration.
- Deterministic Python helpers own inventory, hashes, Git evidence, broken-reference checks, plan validation, dry runs, path confinement, archive moves, transaction journaling, and post-operation verification.
- Scripts are dependency-free, offline, non-interactive, structured-output, idempotent, and dry-run by default.
- The skill uses the portable Agent Skills directory format with supporting `scripts/`, `references/`, and `assets/` resources.
- Python 3 is declared as the recommended compatibility requirement for the safe deterministic path. No package manager, hosted API, or network access is required.

**Runner-up:** a Go helper binary offers stronger standalone performance but requires per-platform releases and creates a second security and distribution surface.

**Rejected:** instructions-only operation is too inconsistent for approval-bound file moves and archive safety across different agent hosts.

## Phase 4 - Architecture ratification

**Chosen seam:** semantic host agent plus one deep deterministic Python module.

- The host agent interprets repository evidence, drafts context changes, explains remediation, and obtains approval.
- The Python module owns inventory, policy enforcement, exact-path planning, state and plan digests, dry runs, transaction recovery, and verification.
- The public Python interface is one `run(request)` function with a closed typed request union.
- Public skill vocabulary remains `scan`, `audit`, and `clean`; internally, `clean` has explicit prepare and commit stages.
- Scan and audit can prepare only a root ledger write. All other mutations require clean.
- Clean approval is bound to the exact snapshot, plan digest, before hashes, and independently approved groups.
- Version 1 exposes only `WriteLedger`, `WritePolicy`, `EditLivingDocument`, `MoveExactPath`, and `ArchiveExactPath` primitives. `WritePolicy` is isolated in its own approved transaction and becomes effective only after a new inspection. The kernel has no delete, shell, callback, glob, arbitrary-write, or network primitive.
- Public third-party operation extensions are deferred. First-party evidence detectors may evolve internally over immutable snapshots without expanding mutation authority.
- New mutations are blocked while a transaction needs verification or rollback.

**Runtime state:** `/overseer.md` remains the only root-level Overseer file. Bounded machine state, journals, archive manifests, and archived files live under `/overseer/`. Machine state never duplicates full document contents or conversation transcripts.

**Interface alternatives considered:** a minimal tokenized three-stage protocol, a mode-first common-caller API, and an extensible protocol engine. The selected design combines the common caller's discoverability with the minimal protocol's explicit phase separation and the extensible design's snapshot, recovery, and closed-primitive discipline. See `references/interface-design-comparison.md` and `references/technical-design.md`.

## Phase 5 - Adversarial validation disposition

The fresh red-team review found specification blockers rather than a false product premise. All blockers were resolved before masterplan authoring.

- `/overseer.md` now has one marker-bounded managed region, a fixed schema, stable IDs, deterministic ordering, byte-level replacement, explicit no-op semantics, a 20-entry history bound, and a 64 KiB managed-block limit.
- Evidence authority is claim-specific. Owner resolutions govern intent, repository configuration and markers govern classification, executable behavior can establish current implementation, documentation owns guidance only within its scope, Git proves change only, and names or timestamps remain hints.
- Equal-strength conflicts, ambiguous canonical business artifacts, unclear nested scopes, and future-versus-current disagreements stop for owner resolution.
- Repository contents are untrusted evidence and cannot grant approval, change safety policy, or instruct tool execution.
- Version 1 defines canonical JSON schemas, domain-separated SHA-256 digests, exact approval envelopes, result variants, stable errors, explicit baseline initialization, and transaction apply terminology.
- Approval binds exact operation IDs and displayed paths in addition to groups, plan digest, snapshot digest, before hashes, expiry, and host attestation. The module validates binding but does not authenticate human identity.
- Cross-group dependencies are shown before approval. A selected subset must be transitively dependency-closed.
- The no-delete promise applies to project content. A confined internal unlink capability may remove verified transaction staging, preimages, locks, and old compact receipts. Archived project content is never purged.
- Rollback stores exact transaction preimages, revalidates before every forward and reverse operation, and never overwrites a conflicting external edit.
- Mutation requires a descriptor-relative no-follow capability probe. Linux and macOS are mutation targets when the probe passes. Windows is inspection and preview only in version 1.
- Archive paths include a transaction boundary to prevent same-day collision while preserving the original relative path.
- Explicit roots, nested-repository boundaries, supported object types, text encodings, metadata preservation, Git fallback, scan closure, secret redaction, and fault injection are specified.

Two suggestions were deliberately rejected:

- A less generic metadata namespace would reduce collision risk, but fixed `/overseer.md` plus `/overseer/` discoverability across agent hosts is more important. Initialization detects and stops on collisions.
- An archive purge command would weaken the owner's chosen archive-only boundary. Overseer removes only its internal recovery material; the owner manually deletes archived project files.

Gate B passed with no open blocker. The full report is in `references/validation-report.md`; resolved contracts are in `references/ledger-contract.md`, `references/protocol-contract.md`, `references/policy-contract.md`, and `references/platform-safety.md`.
